# 项目治理工作流

本 skill 将复杂任务收敛为“取证 → 实现 → 守门 → 验证 → 汇总”。这样做是为了让结论可追溯、避免用历史资料替代当前代码事实，并让规则审查独立于实现者。

规则源：

```text
.claude/rules/core-governance.md
```

长期任务计划：

```text
docs/documentation-governance-plan.md
```

## 0. 先判断任务规模

- **小任务**：单文件、无执行/部署/安全边界变化的机械修正。简述范围 → 最小改动 → 局部验证 → 汇报；不强制调用守门 Agent。
- **复杂任务**：跨多个模块，涉及架构、执行能力、配置、文档事实、路由、确认、部署链路或任一高影响动作。使用本 skill 的完整流程。
- **不确定任务**：先只做取证，得到关键事实后再决定范围；不得用猜测扩张为大项目。

无论任务大小，只要包含删除、覆盖、远端连接/执行、重启、部署、Git commit 或 push，始终遵守核心规则中的用户确认要求。

## 1. 任务合同与计划

复杂任务开始时：

1. 在项目计划中记录：用户请求结果、必须保留的能力、明确排除范围、证据来源、停止条件；
2. 读取与任务相关的当前代码、配置、测试、当前说明和已有 handoff；
3. 区分“代码可证明”“用户明确确认”“仍需环境核验”；
4. 如果关键事实不足，只提出一个最小问题或写明所缺证据，不自行补全假设。

计划文件不存在时才创建它；已有计划时更新相应状态，避免重复造多份工作台账。

## 2. 取证

将需要核验的事实拆成可定位条目。每一条至少记录：

```text
结论 → file:line / 配置键 / 用户确认 → 覆盖范围 → 未知边界
```

优先读取运行入口、调用方、被加载配置和对应测试。历史计划、候选 manifest、脚本阅读副本只能作为线索；它们不能单独证明当前运行或远端部署。

## 3. 实现

1. 只修改已在任务合同内的文件；
2. 执行能力变更时，优先更新精确调用合同、实现、测试与说明，不能只改其中一层；
3. 文档变更必须说明消费者、输入/输出、运行期角色、风险、验证边界与维护责任；
4. 对“当前代码与既定规则冲突”的情况，同时记录真实代码行为和规则冲突；不得用文档措辞消除冲突；
5. 不执行真实部署、远端调用、覆盖、重启、commit 或 push，除非用户在当前上下文明确授权。

需要并行实现时，让写入者使用隔离 worktree；不要让多个 Agent 写同一工作区。

## 4. 守门审查

以下情况在合并结论、提交或进入高影响动作前，调用：

```text
.claude/agents/core-rule-guardian.md
```

向它提供原始用户需求、任务合同、实际 diff、相关代码证据和实际检查结果。守门员只能读、只能裁决。

- `PASS`：可继续到验证或汇总；
- `BLOCK`：停止后续高影响动作，将最小修正写回计划，修正后重新审查；
- 守门 `PASS` 不构成用户对 Git、部署、远端执行或删除的授权。

## 5. 验证

只运行与改动相关、且不会超出已授权范围的本地检查。每项结果记录为：

```text
命令 / 检查 → 通过或失败 → 实际覆盖范围 → 不覆盖什么
```

命令报环境、权限、网络或服务错误时，停止并按核心规则说明证据和处理选项；不要反复尝试替代路径。

## 6. 汇总与交接

汇报保持简短：

1. 已完成的具体改动；
2. 事实证据和验证结果；
3. 仍未核实的环境边界；
4. 被守门阻断的事项与下一步；
5. 是否需要用户决定不可逆或高影响动作。

长期任务结束或切换机器前更新 `SESSION-HANDOFF.md`；稳定规则只维护在 `.claude/rules/core-governance.md`，不复制进 handoff。

热更推进计划看板为 `docs/hotfix-requirements-progress.html`：进度更新只改其中的 `PLAN_DATA`（每个 step 的 `done` / `current` / `remaining` 数组与 `status` 三态），不改样式与渲染函数；页面顶部注释与 `docs/hotfix-execution-master-plan.md` §7 有完整约定。
