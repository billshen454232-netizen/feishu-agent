# 执行结果确定性展示与典型故障库

> **状态：首期已实现（2026-11-03，本地测试通过，未部署）**  
> **日期：2026-11-02**  
> **关联计划：** [项目计划看板](../../hotfix-requirements-progress.html) STEP 24  
> **不变原则：** Worker/Gateway 已验证并持久化的终态是唯一权威；模板、故障库和 AI 都只能解释，不能改变终态。

## 1. 目标

减少执行结果研读的 AI 压力，避免日志分析超时阻塞结果投递，并沉淀可审核、可复用的典型故障报告。

```text
成功 / 结果未知
→ 确定性模板
→ 不调用 AI

失败
→ 错误特征命中模板库（可用 或 待审核）
→ 直接复用诊断模板，卡片注明来源
→ 不调用 AI

未知失败（模板库未命中）
→ 立即发可信保底失败卡
→ 后台 AI 分析
→ 自动收集为「待审核」模板（之后同类错误直接复用，不再调 AI）
→ 运行一段时间后，人工在网页统一审批 → 移入「可用模板」
```

## 2. 分流规则

| 可信终态 | 默认展示 | 是否调用 AI | 原因 |
| --- | --- | --- | --- |
| `done` | 确定性成功模板 + 执行明细 | 否 | 成功状态和步骤事实已足够，完整日志分析不增加可信度。 |
| `submitted_result_unknown` | 确定性未知模板，明确“请勿重复确认或重试” | 否 | 未知不是失败，不能由 AI 猜测原因或建议重放。 |
| `failed` + 命中可用模板 | 失败模板 + 典型故障说明（已审核） | 否 | 已有经审核的诊断，避免重复消耗 AI。 |
| `failed` + 命中待审核模板 | 失败模板 + 说明（AI 分析 · 未人工确认 · 已复用 N 次） | 否 | 同类错误不重复调 AI；标签提示结论尚未确认。 |
| `failed` + 未命中 | 立即发失败保底卡 | 后台调用 | AI 结果自动收集为待审核模板；不能阻塞 Worker 回传或第一张结果卡。 |

## 3. 不混淆两种“缓存”

### 3.1 报告缓存（本设计范围）

**每次操作仍照常执行**；只是相同的已知失败不重复请 AI 写解释。

适用：写操作、读操作、失败诊断。

```text
本次结果 → 错误特征命中 → 复用“为什么失败 / 如何核验”的报告模板
```

### 3.2 执行结果缓存（不在本次范围）

**不执行 Muliu，直接返回旧结果**。只可能用于登记为 `read` 的查询，并且必须有短 TTL、生成时间、路由/环境、脚本版本等严格条件。

绝不能用于：合服、起服、关服、清档、Patch、改配置等写操作。

```text
同样的 2213 → 2018 合服参数
≠ 同一个环境状态
≠ 可以跳过执行
```

## 4. 故障特征：不能只按参数匹配

“参数相同”不足以说明故障原因相同；反过来，**参数不同也可能是同一种典型错误**（2213→2018 和 3001→3002 都可能是 SSH 255）。因此匹配键只取与错误本身相关的部分：

```text
匹配键 = hash(
  脚本 path
  + 稳定失败类别（退出码 / HTTP 状态 / 受控错误码）
  + 规范化 failure_reason
  + 规范化关键错误行（见 4.3）
)
```

以下**只记录、不参与匹配**，用于网页展示「出现过的范围」：

```text
args、route_region、catalog 版本、出现时间、message_id
```

不把 catalog 版本放进匹配键：catalog 改动频繁（加阈值、改路由），否则每次改动都会让整个模板库失效。

### 4.1 归一化

错误特征生成前必须替换：

```text
IP、URL 凭据、Token、Cookie、数据库连接、临时路径、UUID、时间戳、请求 ID
```

不得过度移除：

```text
退出码、HTTP 状态、脚本名、稳定错误码、关键组件名、已登记路径
```

否则不同根因会误命中成同一种故障。

### 4.2 精确匹配优先

首期只允许：

```text
匹配键完全相同
→ 命中模板（可用 或 待审核）
→ 复用报告，卡片注明来源
```

不使用向量相似度或模糊自然语言自动套用结论。未来若增加“相似案例”，只能提示参考，不能自动给出根因或执行建议。

### 4.3 关键错误行的确定性提取

同一错误每次必须算出同一个匹配键，因此提取规则必须是确定的程序规则：

1. 在清洗后的步骤日志中，取**最后 K 条**命中错误关键词的行（关键词表如 `error`、`Error`、`Traceback`、`失败`、`异常`、`exit code`、`Permission denied`、`Connection refused`，可配置）；
2. 没有命中时，取日志**尾部 K 行**；
3. 对这些行先做 4.1 归一化（IP、时间戳、UUID、临时路径、请求 ID 等替换为占位符），再参与 hash；
4. K 与关键词表属于配置，变更后旧模板可能不再命中——这是预期行为，网页可按新规则重算。

实施时用至少 3 份真实失败日志作为测试样本：同一错误跨服号/跨时间必须得到相同匹配键，不同错误必须不同。

## 5. 数据模型

在现有 Gateway SQLite 的 `message_jobs` 库中新增结构化表，不复用 Markdown 会话归档。

### 5.1 `execution_artifacts`

每次可信终态的脱敏执行事实。

| 字段 | 含义 |
| --- | --- |
| `message_id` | 与 `message_jobs` 一对一 |
| `plan_fingerprint` | 规范化 path + args + route 的 hash |
| `terminal_status` | `done` / `failed` / `submitted_result_unknown` |
| `failure_reason` / `unknown_reason` | 脱敏原因 |
| `redacted_steps_json` | 脱敏后的步骤事实与关键日志摘要 |
| `error_fingerprint` | failed 时的结构化签名 |
| `catalog_version` | 合同版本 / 内容摘要 |
| `created_at` | 事实生成时间 |

### 5.2 `execution_error_patterns`

已知错误库。

| 字段 | 含义 |
| --- | --- |
| `pattern_id` | 主键 |
| `script_path` | 脚本 |
| `error_fingerprint` | 精确匹配键（唯一） |
| `key_error_lines` | 归一化后的关键错误行（网页展示用） |
| `diagnosis_template` | 诊断与核验建议（AI 初稿，可人工编辑） |
| `status` | `candidate`（待审核）/ `verified`（可用） |
| `seen_scopes_json` | 出现过的 args / route_region 摘要（只展示，不匹配） |
| `sample_message_ids` | 最近几次关联执行，便于审批时对照原始结果 |
| `first_seen_at` / `last_seen_at` / `hit_count` | 统计 |
| `approved_at` | 最近一次审批时间 |

删除即物理删除该行；被删除的错误下次出现时会重新走 AI 并重新收集为待审核。

### 5.3 `execution_interpretations`

未命中失败的后台 AI 研读任务，复用 [AI 研读可靠性设计](2026-11-02-execution-interpretation-reliability.md) 的持久化任务机制。

| 字段 | 含义 |
| --- | --- |
| `message_id` | 关联执行事实 |
| `status` | `pending` / `running` / `done` / `failed` / `timed_out` |
| `summary` | 脱敏 AI 候选分析 |
| `model_name` / `elapsed_ms` / `input_chars` | 可观测性 |
| `candidate_pattern_id` | 可选：待审核模式 |

## 6. 卡片展示

飞书结果卡固定三层：

```text
【权威终态】执行完成 / 执行失败 / 结果尚未核验
【执行证据】步骤、可信失败原因、受控执行明细
【结果说明】程序模板 / 已命中典型故障 / AI 新分析
```

### 6.1 已命中模板

可用模板：

```text
说明来源：已审核典型故障（命中 N 次）
诊断：...
建议：只给核验/排查建议，不自动重试写操作
```

待审核模板：

```text
说明来源：AI 分析 · 未人工确认（已复用 N 次）
诊断：...
```

### 6.2 成功卡片内容

写操作成功不调用 AI，卡片固定展示「【执行完成】摘要 + 步骤列表（编号、成功/失败、描述）」。状态卡不放原始日志（沿用现有原则）；需要日志时按原有 `include_execution_logs` 另发明细消息。

查询类（全部步骤命中 `risk=read` 合同）成功：由审批页开关决定——「AI 后台解读」（默认）先发程序卡，后台读日志后更新卡片；「只发程序模板」则不调用 AI。

### 6.3 AI 新分析

AI 分析成功后只更新原卡片的“结果说明”区域：

```text
说明来源：AI 新分析（待人工确认）
可信终态仍为：执行失败
```

AI 超时/失败时保留已发出的保底卡，不重复发消息、不改状态。

## 7. 网页审批

运行期间 AI 分析自动收集为待审核模板并被复用；运行一段时间后，人工在网页统一审批。

### 7.1 两个页签

| 页签 | 内容 | 可做的操作 |
| --- | --- | --- |
| **待审核** | 所有 `candidate`，按命中次数倒序 | 查看、编辑诊断文本、**通过**（移入可用）、**删除**；支持勾选批量通过 / 批量删除 |
| **可用模板** | 所有 `verified` | 查看、编辑诊断文本、**退回未审核**、**删除** |
| **最近执行**（只读） | 最近 50 条执行：请求与发起人昵称、需求分析模型 / 耗时 / 调用次数、终态、说明来源（程序模板 / AI 解读 / 模板复用 / AI 新分析）、模型、耗时、AI 说明 | 只看不改；用于核对 AI 解读质量与耗时。成功结果不生成模板（状态类结论不可复用） |

```text
AI 分析 ──自动收集──→ 待审核 ──通过──→ 可用模板
                       ↑  │               │
                       │  删除          退回未审核 / 删除
                       └──────────────────┘
```

### 7.2 每条模板展示

- 脚本、失败类别（退出码等）、归一化关键错误行；
- 诊断文本（可编辑）；
- 命中次数、首次 / 最近出现时间；
- 出现过的范围（服号、区域摘要）；
- 最近几次关联执行的脱敏结果摘要，用于对照判断 AI 结论是否正确。

### 7.3 状态语义

- 待审核和可用模板**都会被命中复用**，区别只在卡片来源标签（见 6.1）；
- 通过 / 退回只改标签，不改匹配；
- 删除后该错误下次出现会重新走 AI、重新进入待审核——适合「AI 结论错了，想让它重新分析」。

### 7.3.1 结果判定（人工纠正）

每条模板有「结果判定」：`执行失败`（默认）或 `执行成功 · 服务器状态存疑`。

适用场景：查询脚本按约定以非 0 退出表示「服务器状态异常」（如 `basic_info.sh` 发现开服时间文件缺失、未检测到开服成功信息），查询本身是成功的。

生效条件（三者同时满足）：

1. 模板为**可用模板**（人工已通过）；待审核模板、AI 新分析一律按失败展示；
2. 判定为 `执行成功 · 服务器状态存疑`；
3. 本次结果所有步骤命中 `risk=read` 合同；写操作失败永远按失败展示。

效果：卡片为橙色「测试服查询完成 · 服务器状态存疑」，正文写明机器判定原文与模板诊断；**数据库与审计中的终态仍为 `failed`**，「最近执行」显示来源「复用可用模板 · 判定警告」。

### 7.4 部署位置与访问

> **决策变更（2026-11-03 晚）**：最初决定「只经 SSH 隧道访问、不对公网开放」；当晚改为**经 Cloudflare Access 对外访问，源站自行校验 Access 令牌**。下面是当前做法与理由，旧做法保留为备用通道。

审批页仍是 Gateway 进程内**独立监听 `127.0.0.1:<admin_port>` 的第二个服务**（不挂在对外的 FastAPI 应用上），有两条访问通道：

```text
公网：浏览器 → Cloudflare（Access 应用 ops，策略 owner-only，Google 登录）
      → 阿里云 nginx ops.ttlink.asia（源站证书 ttlink-origin）
      → 127.0.0.1:8901（审批页自行校验 Access JWT）
备用：ssh -L 8901:127.0.0.1:8901 <gateway> → http://127.0.0.1:8901（不需要令牌）
```

**为什么不能只靠 Cloudflare 邮箱认证**：Access 只拦经过 Cloudflare 的请求；知道源站 IP 的人可以直连 443、带上 `Host: ops.ttlink.asia` 绕过。nginx 也无法按 Cloudflare IP 段限制来源（这台机器开了 `real_ip`，看到的是真实用户 IP）。所以审批页自己校验令牌。

实现约束（代码：`src/access_auth.py`、`src/admin_app.py`）：

- nginx 对每个转发请求**强制设置** `X-Admin-Proxy: cloudflare-access` 和 `Host: 127.0.0.1`（客户端无法去掉或伪造）；
- 带该标记的请求必须携带有效的 `Cf-Access-Jwt-Assertion`（或 `CF_Authorization` cookie）：RS256 签名对团队公钥（`https://<team>/cdn-cgi/access/certs`，缓存 1 小时，未知 kid 时刷新）、`aud` = 应用 AUD 标签、`iss` = 团队域名、未过期；否则 403；
- `admin.access_team_domain` / `admin.access_aud` 未配置时，公网请求一律 403（失败即关闭）；
- 不带标记的请求只能来自 127.0.0.1（SSH 隧道），照常放行；Host 必须是回环地址（防 DNS 重绑定），写操作必须带 `X-Admin-Request: 1`（防跨站提交）；
- 审批改动日志记录操作人邮箱（`operator=`），隧道访问记为 `ssh-tunnel`；
- 依赖 `PyJWT[crypto]==2.10.1`；`admin_port` 仍不在安全组放行。

当前部署（2026-11-03）：

| 项 | 值 |
| --- | --- |
| 域名 | `ops.ttlink.asia`（Cloudflare 代理开启） |
| Cloudflare Access | 应用 `ops`，策略 `owner-only`，登录方式 Google，会话 24 小时 |
| 团队域名 | `billshen454232.cloudflareaccess.com` |
| nginx | `/etc/nginx/sites-available/ops.ttlink.asia.conf`（已启用），证书 `/etc/ssl/cloudflare/ttlink-origin.{pem,key}` |
| Gateway 配置 | `config.json` → `admin.enabled / port / access_team_domain / access_aud` |

上线验收（均已通过）：经 Cloudflare 访问 → 302 到 Access 登录；直连源站 IP 无令牌 / 伪造令牌 → 403；SSH 隧道 → 200；其他站点不受影响。

**回退**：删除 `sites-enabled/ops.ttlink.asia.conf` 并 `nginx -t && systemctl reload nginx`，即回到仅 SSH 隧道访问；审批页本身无需改动。

与 [热更阈值网页管理](2026-10-30-threshold-registry-web.md)（开发机）是两个独立页面，后续可统一入口。

## 8. 实施顺序

1. 提取并持久化可信 `execution_artifacts`；
2. 成功和未知结果改为确定性模板，移除 AI 研读调用；
3. `failed` 结果按 4.3 计算匹配键，查询模板库（待审核 + 可用）；
4. 命中则直接展示模板，未命中先投递保底卡；
5. 接入后台 `execution_interpretations`，AI 只分析未命中失败；
6. AI 结果自动写入待审核模板；
7. 审批网页（两个页签、通过 / 退回 / 删除 / 编辑 / 批量）；
8. 为研读补专用预算、模型 deadline 和可观测性；
9. 补全测试与小范围部署评测。

`execution_artifacts` 保留 90 天后清理（可配置）；模板库不随之清理。

## 9. 验收标准

1. 成功结果与 `submitted_result_unknown` 的 AI 调用次数为 0；
2. 命中模板（待审核或可用）时 AI 调用次数为 0；同一新错误第二次出现不再调 AI；
3. 未知失败先展示可信保底卡，Worker `/result` 不等待 AI；
4. AI 结果无法改变终态、卡片颜色、审计状态；
5. 待审核模板不会自动变为可用模板，卡片标签如实区分两者；
6. 不同错误特征不复用诊断；同一错误在不同服号/参数下命中同一模板；
7. 写操作永不跳过真实执行；
8. 可以追踪每次报告是程序模板、可用模板、待审核模板还是 AI 新分析；
9. 网页可批量通过、退回未审核、删除；删除后同类错误重新走 AI 收集。
