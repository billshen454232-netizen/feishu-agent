# GVG 依赖游戏服的断连与优雅关停设计

> **状态：本地实现 / 待部署验收**
>
> **日期：2026-11-17**
>
> **目标：** 在关闭国服某套 GVG 环境前，先有序断开所有依赖游戏服到 GVG 的连接，避免 GVG 因仍有游戏服连接而无法正常关停；不得以 `kill` 代替正常流程，也不得引发连接重试风暴和大量服务端告警。

## 1. 现状与已核实证据

### 1.1 国服 GVG 环境映射

现有 `shutdown` / `start` 脚本中的固定映射：

| 环境 | 服务器 |
| --- | --- |
| `weeklygvg` | 2022、2023、2024、2025 |
| `devgvg` | 2026、2027 |
| `qagvg` | 2028、2029 |

`qagvg` 的第一个服务器（2028）为 GVG zone 启动节点，后续服务器（2029）为 daemon 启动节点；启动脚本顺序为先 zone、等待 15 秒、再起 daemon。

### 1.2 现有“normal”实现不是真正优雅停服

当前 `/home/serverGeneralScript/shutdown` 对 `weeklygvg` / `devgvg` / `qagvg` 的 `normal`、`autokill`、`kill` 三种参数都走：

```text
每个 GVG 主机执行 kill_gvg_zone.sh
→ 等待 5 秒
→ 每个 GVG 主机执行 kill_gvg_zone_daemon.sh
```

因此其中的 `normal` 名称不代表调用服务的优雅退出流程；它本质上仍是 kill 路线。若仍有普通游戏服与 GVG 保持连接，服务端已反馈此路线会导致正常关停失败，而强杀会让游戏服持续重连、触发大量飞书告警。

### 1.3 已确认的游戏服侧 GVG 连接配置（2026-11-17）

对一台国服普通游戏服执行 `basic_info.sh` 的输出，已确认：

```lua
NSLG_GVGZONENUM = 4
```

`basic_info.sh` 的首段直接读取 `/data/app/etc/nslg_game.lua`，所以已确认的**游戏服侧配置入口**为：

```text
/data/app/etc/nslg_game.lua
```

`NSLG_GVGZONENUM` 是游戏服连接 GVG 的运行配置：

- 有效赋值（例如 `= 4`）表示连接对应 GVG zone；
- 将这一行按 Lua 语法注释后，重启该服的 **game 服务**，该游戏服不再连接 GVG；
- 恢复该行并重启 game 服务后，游戏服重新连接 GVG；
- 这是当前已确认、可作为第一版“连接排空”手段的事实；无需猜测 `gvg_zone-etc` 中的字段。

> [!warning] 仍未确认的边界
>
> - 用户已确认 `weeklygvg` 对应集群 `4`，DEV 和 QA 的 GVG 集群编号待核实。依赖服清单以各服最新配置为准。
> - 尚未确认是否存在游戏内 RPC / 控制台命令可让 game 服务主动注销 GVG 连接。它若存在，可作为后续优于“改配置 + 重启”的优化方案；在取得代码或控制台证据前不可假设。
> - 已确认“注释配置后重启 game 生效”，但尚未定义 GVG 侧的零连接可信观测指标，也未确认 GVG 自身真正的优雅退出入口。

`/data/app/gvg_zone-etc/server_cluster_config.lua` 仍是 GVG 自身的额外运行配置，但不是本需求中普通游戏服连接 GVG 的开关。

## 2. 目标能力

为指定 GVG 环境（`weeklygvg` / `devgvg` / `qagvg`）提供一个受控流程，而不是开放任意远程配置编辑：

```text
预检
→ 识别该环境依赖的游戏服清单
→ 备份并暂时关闭游戏服到 GVG 的连接配置
→ 让配置生效（只使用经确认的 reload / restart 方式）
→ 轮询确认 GVG 无剩余游戏服连接
→ 正常关闭 GVG zone / daemon
→ （按用户选择）保留断连状态或恢复连接配置
→ 输出审计与验证报告
```

### 非目标

- 不开放任意 Lua 键、任意路径、任意 shell 或任意服务器批量修改。
- 不在未确认具体配置键前自动操作。
- 不把“关服失败”自动升级为 kill。
- 不自动消除或绕过服务端告警；应通过正确的连接排空减少告警根因。

## 3. 调研任务：先在目标机验证

必须通过已授权的 GS-1 只读路径，选取一个**明确连接目标 GVG 环境的普通游戏服**，收集以下最小证据。不得收集账号、数据库、密钥、密码、完整私有配置或业务数据。

| 问题 | 需要的只读证据 | 通过标准 |
| --- | --- | --- |
| 游戏服从哪里读取 GVG 地址/开关 | 配置文件路径、非敏感字段名、引用链 | 能定位唯一或优先级明确的配置来源 |
| 配置生效方式 | 代码/运维脚本中的 reload、重启或注册流程 | 能证明无需猜测地断开连接 |
| 哪些游戏服依赖该 GVG 环境 | 环境映射或运行服务发现清单 | 清单可从受控配置/服务端 API 得到 |
| GVG 已无连接怎么判断 | GVG 日志、状态接口或进程指标 | 有零连接/连接清空的确定性条件 |
| 正常关闭入口 | 服务端提供的优雅退出脚本/API与完成标记 | 有退出成功的可信终态 |
| 恢复方式 | 配置备份/版本、恢复后连接和健康检查 | 可一键或按清单回滚 |

调研输出只记录脱敏后的字段名、相对路径、服务关系和验证结论。

## 4. 推荐实现形态

### 4.1 配置驱动的受控注册表

不要把游戏服列表写死在 shell 脚本。新增独立、版本管理的 GVG 依赖注册表，内容由第 3 节调研结果填写：

```yaml
# 仅展示数据形状；环境映射、依赖服清单和检查命令仍待取证
qagvg:
  gvg_servers: [2028, 2029]
  dependent_game_environments: [qa]
  connection_switch:
    file: /data/app/etc/nslg_game.lua
    key: NSLG_GVGZONENUM
    disabled_action: comment_assignment
    enabled_action: restore_assignment_from_backup
    apply: restart_game_only  # 已确认需重启 game；具体受控入口待实现
  drain_check: <待确认的 GVG 零连接检查>
```

注册表必须限定：环境名、经确认的配置文件/键、允许写入值、受影响游戏服来源、应用方式、检查方式。执行器不能接收自由路径、自由键或自由值。

### 4.2 两阶段执行

#### 阶段 A：连接排空（可回滚）

1. 加载环境依赖清单，展示将受影响的游戏服；
2. 对每个文件做时间戳备份和内容哈希记录；
3. 仅修改已登记的连接开关；
4. 使用已登记的方式让配置生效；
5. 对每台游戏服验证连接已断；
6. 对 GVG 侧验证无依赖连接；若任一项失败，停止，不进入停 GVG 阶段，并提示恢复或人工处理。

#### 阶段 B：优雅关停 GVG（高影响，单独确认）

1. 再次检查零连接；
2. 调用已确认的优雅退出入口；
3. 等待可信退出终态；
4. 超时或失败只报告证据，**不自动 kill**；
5. 输出备份位置、修改列表、连接排空结果和停服结果。

### 4.3 恢复策略

必须让请求者在确认卡中选择意图：

- **维护停服**：保留游戏服断连配置，直到显式恢复；
- **临时重启 GVG**：GVG 重新健康后，恢复原连接配置并按确认的方式让游戏服重新连接。

恢复也是写操作，应有独立确认和健康检查；不得因关闭失败自动恢复/重启，避免掩盖现场。

## 5. 飞书机器人与审计要求

- 新能力属于高影响写操作，必须通过现有严格 `path + args` 合同、路由校验和群内确认卡。
- 确认卡必须列出：目标 GVG 环境、受影响普通游戏服数量/清单、断连方式摘要、是否保留断连、是否将执行 GVG 优雅关停。
- 计划、飞书卡片、日志、Vault 不得包含 IP、账号、密码、Token、完整配置内容或数据库连接串。
- 失败必须记录：当前阶段、已完成步骤、未完成步骤、备份标识、是否已修改配置、已确认的零连接证据或证据缺口。
- 既有 `shutdown qagvg normal` 不得重命名为优雅关停，除非实现与测试都已替换其 kill 路径；为了兼容，应先新增显式能力并保留旧行为说明。

## 6. 验收标准

在专用测试环境验证：

1. 未配置/未登记环境会被拒绝，且不修改任何文件；
2. 预检能列出完整受影响游戏服；
3. 断连配置修改有逐文件备份，重复执行保持幂等；
4. 配置应用后，游戏服不再发起 GVG 连接，GVG 侧可观测为零连接；
5. GVG 正常退出，无强杀、无连接重试风暴；
6. GVG 无法退出时，不自动 kill，能给出可信日志/状态证据；
7. 恢复时，仅恢复该次备份涉及的配置，游戏服重新连接且健康检查通过；
8. 全程无敏感信息进入 Git、飞书、AI 或 Vault。

## 8. 木流拓扑启停复用

2026-11-25 的 Task 587 和 Task 588 均以 GVG 集群号 `4` 为目标。停服先根据拓扑和活跃进程筛选入批的游戏服，经 `RpcStartShutdown` 等 RPC 关停并验证退出，随后关闭 `gvg_zone`。起服重新计算目标的启动依赖，运行中的依赖会跳过，然后根据实际主从拓扑启动 GVG 并等待业务成功标记。本次 Task 588 的记录为一台主节点、两台 Daemon。停服与起服清单各自计算，恢复原来停掉的游戏服需要独立步骤。

采用现有 Worker → Task 89 → GS-1 的通道，复用 `discover_game_server_topology.py`、`shutdown_game_server_by_topology.py` 和 `start_game_server_by_topology.py`。查询以实时拓扑为准，分别展示 GVG Zone 的运行态报告、运行中的依赖游戏服及配置指向 GVG 但已停的游戏服。按变更单写连接配置仍从 Server Manager 读取文件原值和版本。

启停预检调用原执行器的计划生成阶段，回传待确认批次。GS-1 在真正发指令前核对计划指纹，名单、节点或执行顺序漂移时重新预检。每次调用用独立工作目录，结果只回传集群、服号、角色和终态。恢复被停的普通服仍由操作者发起。拓扑查询和启停覆盖国服 Weekly `4`、DEV `260005`、QA `260006`。Task 587、588 的快照分别将三组集群的主节点对应到 2022、2026、2028。QA 的旧脚本还登记了 2029，实际启停成员由每次扫描决定。
