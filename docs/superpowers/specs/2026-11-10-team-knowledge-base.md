> **日期：2026-11-10**

## 1. 目标与使用者

组员（数据也来自组员）在飞书问机器人，或直接在内网浏览：

| 问题类型 | 例子 | 依赖的数据 |
| --- | --- | --- |
| 谁负责 / 谁测过 | 「亲卫队之前是谁测的？对应的策划、程序是谁？」 | 功能登记表（§3.3） |
| 类似功能参考 | 「我要测一个新的同盟建筑，之前有没有类似的？」 | 功能卡片（§3.2）的简介 / 关键词 |
| 注意事项 | 「测水战相关功能要注意什么？」 | 相关功能的 P0 用例、备注、卡片测试关注点 |
| 具体用例 | 「补兵额度用完后界面显示什么？」 | 规范化用例（§3.1） |

要求：存放在内网（Worker 机器）、更新方便（组员自己上传）、大家都能查阅。规模：现在几 MB，全员上传后十几 MB，Markdown + 关键词检索够用；更大或检索效果不够时再上向量库（§8）。

## 2. 总体架构

```text
组员 ──网页上传（/upload.html）──► team-kb 服务（Worker，127.0.0.1:8091，经 nginx 8090 的 /api/）
                                  ├─ 校验（敏感信息扫描、大小、格式；不通过不入库）
                                  ├─ 规范化（tools/team_kb/normalize.py）
                                  ├─ 重建浏览站与 index.md（tools/team_kb/build_site.py）
                                  ├─ 本地 git 提交，作者 = 上传人（只在 Worker 本地，便于回滚；不推送）
                                  ├─ 刷新内存搜索索引
                                  └─ 后台队列：外部 AI 生成功能卡片（§3.2）→ 写 cards/、重建、提交、刷新索引
组员 ──浏览器（内网 :8090）──► nginx：docsify 静态站 + 侧栏搜索框（调用 /api/search，服务端检索）
组员 ──飞书提问──► Gateway ──（队列）──► Worker：检索 + 生成回答 ──► Gateway 回复飞书
```

- **数据只存 Worker**：Gateway（公网）不保存知识库内容，只转发问题和回答。
- **Gateway 不能主动访问 Worker**（Worker 主动拉取任务），所以飞书问答走现有任务队列：新增任务类型「组内知识问答」，由 Worker 认领、检索、调用 AI 生成回答后交回 Gateway。

## 3. 数据模型（`/opt/team-kb`）

```text
/opt/team-kb/
  inbox/<上传批次>/          原始上传（保留，便于追溯）
  cases/<组别>/<作者>/<功能>.md   规范化用例（frontmatter + 统一表头；§3.1）
  cards/<功能>.md            功能卡片（§3.2）
  registry/features.csv     功能登记表（§3.3）
  index.md                  自动生成：按组别 / 功能 / 作者的总索引
  site/                     docsify 入口（index.html、_sidebar.md 自动生成）
```

### 3.1 规范化用例

沿用第 2 步已验证的规则：统一表头 `模块|二级模块|分级|测试项|前置条件|执行步骤|预期结果|实际结果|备注`；Excel 合并单元格向下填充模块 / 二级模块；空分级标「未分级」，不猜；其他表格与正文原样保留。frontmatter：功能名、组别、作者、来源、用例数、分级统计、模块列表、上传人、上传时间。

### 3.2 功能卡片

字段与第 2 步一致：一句话、简介、测试关注点、关键词、典型问题。上传后自动生成（Worker 调用 AI，规则同 `kb_card_prompt.md`，实现 `tools/team_kb/cards.py`）；已有卡片在用例未变时不重生成，用例更新则重生成。

- 发给 AI 的只有摘要：功能名、组别、作者、用例数、模块结构、最多 8 条样例（P0 优先），且所有命中敏感规则的值先打码（`normalize.mask_text`）；全文不出内网。Excel 单元格换行拆出的残片行（模块列是「2.停起服」之类）不进摘要。
- 模型配置在 Worker 的 `/opt/team-kb/ai.json`（chmod 600，不进任何 git）：与 Gateway 相同的中转，按顺序尝试，前一个失败或输出格式不符时换下一个。
- team-kb 服务后台单线程排队生成（一次 10–60 秒），上传结果提示「AI 在后台生成」；失败重试一次，仍失败只记日志，页面保持无卡片。生成期间用例又被更新则丢弃这次结果（新上传已重新排队）。
- 卡片提交到知识库本地 git，作者「AI 卡片」，说明里写模型名。
- 存量缺卡片的文件可手动补：`cards.py --missing [--limit N] [--write]`（不带 `--write` 只打印；写入后重启 team-kb 刷新索引）。

### 3.3 功能登记表（谁负责）

现有用例里只有「作者（测试）」，**没有策划、程序信息**，需要人工维护：

| 功能 | 别名 | 组别 | 测试 | 策划 | 程序 | 首次上线（赛季/版本） | 状态 | 相关功能 | 备注 |

- 初始版由脚本从用例生成（功能、组别、测试 = 作者），策划 / 程序留空；
- 组员通过上传 Excel / CSV 更新（网页上传，后续阶段），按「功能」合并，不整表覆盖。

## 4. 更新流程（组员，网页上传）

用户 2026-11-11 决定用网页上传（不用 Jenkins）。内网、无登录，靠「上传人必填 + 本地 git 记录作者 + 可回滚」追溯。

1. 浏览站侧栏「上传 / 更新资料」→ `upload.html`：上传人（必填，浏览器记住）、组别（系统组 / 赛季组 / 国服 / 其他）、测试（作者，默认同上传人）、`.md` 文件（一次 ≤ 20 个，每个 ≤ 3 MB）。
2. 浏览器读原始字节（base64）上传，服务端识别 UTF-8 / GBK。
3. 校验：文件名只能是 `.md`、不含路径字符，否则拒绝。命中 IP、密码、token、手机号、数据库地址规则的文件**不直接拒绝，交管理员审核**（§4.1）。
4. 规范化后写 `cases/<组别>/<测试>/<文件名>`：同路径 = 更新（内容相同显示「无变化」，不产生版本）；不同测试写同一功能 = 并存。Obsidian 属性块保留为一行「原文档属性」。
5. 结果表：新增 / 已更新 / 无变化 / 已拒绝，用例数、未分级数、提示（单元格换行串行、分级列混入文字、暂无或过期的摘要卡片）。
6. 原始上传保存在 `inbox/<时间>-<上传人>/`；浏览站与搜索在上传完成后立即更新。

### 4.1 命中规则的文件：管理员审核（2026-11-11 用户决定）

规则是固定正则，会误判（测试服 IP、文档里的示例密码等），目标机器也都在内网，所以不一刀切拒绝：

- Worker 把文件放进 `pending/<编号>/`（原文、规范化结果、元数据），上传人看到「待审核」。
- team-kb 服务每 15 秒把**未上报**的待审核项推给 Gateway（`POST /internal/team-kb/reviews`，Worker 令牌）：只含文件名、上传人、组别、目标路径、用例数、命中类型与行号、**命中值部分打码的命中行**（如 `10.***.40`、`密码：hu***22`），以及「内网查看全文」链接（`<内网站点>/api/pending/<编号>`，只有在内网能打开）。原文不离开 Worker。
- 运维页（ops，Cloudflare Access 仅管理员）新增「知识库审核」页签：待审核 / 已通过 / 已拒绝；可填备注，「通过并入库」或「拒绝」，记录审核人。
- team-kb 服务拉取决定（`GET /internal/team-kb/decisions`）：通过 → 写入 `cases/`、重建站点、本地 git 提交（作者 = 上传人，提交说明注明审核人）、刷新搜索；拒绝 → 移到 `pending/_rejected/`。结果回报 Gateway（`POST .../applied`），页面显示「已在内网处理」或失败原因。
- `pending/` 不进知识库 git，也不在静态站点目录下。

**功能卡片自动生成**：已接入（2026-11-11，见 §3.2）。未配置 `ai.json` 时自动关闭，上传结果提示「暂无摘要卡片」。

Excel 原件转换器（处理合并单元格、单元格内换行）是后续阶段的事；在此之前，单元格换行导致串行的文件在上传结果里提示「建议上传 Excel 原件或重新导出」。

## 5. 飞书问答

- **意图**：意图路由新增「组内知识」类，与「测试服操作」「脚本知识问答」区分。
- **检索（Worker 上）**：
  1. 功能级：在卡片（功能名、别名、关键词、简介）和登记表中检索，得到候选功能；
  2. 用例级：在候选功能的用例行里按问题关键词检索（中文二元组 + 文档频率加权，复用 `ScriptKnowledgeBase` 的做法）；
  3. 「谁负责」类问题直接读登记表，不需要 AI 生成内容之外的推断。
- **回答**：给 AI 的上下文只包含命中的卡片、登记表行和少量用例行；回答必须注明来源（功能 + 作者 + 文件），信息不足时直说，不编造人员或配置。
- **并发**：Worker 目前一次只执行一个任务，长时间操作（如合服）会让问答排队；知识问答需要独立的认领通道，不与测试服操作互相阻塞。

## 6. 浏览与搜索（内网）

- nginx 8090：根目录 `/opt/team-kb/site`（docsify 4.13.1，资源随站点存放，不依赖外网）；`/api/` 转发到 team-kb 服务。
- **搜索在服务端做**：docsify 自带搜索要在浏览器下载全部页面（4.5 MB）并在每次按键时扫描约 2.4 万行，明显卡顿（与 Python 版本无关：静态站点不经过 Python）。现由 team-kb 服务在内存里保存每条用例行与每个功能的摘要，按词全匹配优先、否则按中文二元组覆盖率（≥ 60%）排序，P0 略优先；单次查询约 20–40 ms，只返回前 10 个功能与前 40 条用例。
- 前端：侧栏搜索框停止输入 250 ms 后查询，结果高亮；点用例结果会跳到对应页面并定位、高亮那一行。

## 7. 检索效果评估

卡片里的「典型问题」（133 × 3 ≈ 400 条）直接作为评测集：问题 → 期望命中的功能。每次改检索规则后跑一遍，看命中率；登记表类问题另写 20 条。

## 8. 何时升级到向量库

满足任一条件再考虑 Dify（Worker 已部署）或自建向量检索：数据量超过约 50 MB；评测集命中率在关键词检索下明显不够；或需要按语义找「类似功能」。Worker 上 Ollama 已有 `bge-m3` 嵌入模型，可直接复用。Markdown 仍是唯一数据源，向量库只是可重建的索引。
