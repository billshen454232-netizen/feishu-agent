> **日期：2026-11-10**

## 1. 目标与使用者

组员（数据也来自组员）在飞书问机器人，或直接在内网浏览：

| 问题类型 | 例子 | 依赖的数据 |
| --- | --- | --- |
| 谁负责 / 谁测过 | 「亲卫队之前是谁测的？对应的策划、程序是谁？」 | 功能登记表（§3.3） |
| 类似功能参考 | 「我要测一个新的同盟建筑，之前有没有类似的？」 | 功能卡片（§3.2）的简介 / 关键词 |
| 注意事项 | 「测水战相关功能要注意什么？」 | 相关功能的 P0 用例、备注、卡片测试关注点 |
| 具体用例 | 「补兵额度用完后界面显示什么？」 | 规范化用例（§3.1） |

要求：存放在内网（Worker 机器）、更新方便（组员自己上传）、大家都能查阅。规模：现在几 MB，全员上传后十几 MB，Markdown + 关键词检索够用；更大或检索效果不够时再上向量库（§8）。

## 2. 总体架构

```text
组员 ──网页上传（/upload.html）──► team-kb 服务（Worker，127.0.0.1:8091，经 nginx 8090 的 /api/）
                                  ├─ 校验（敏感信息扫描、大小、格式；不通过不入库）
                                  ├─ 规范化（tools/team_kb/normalize.py）
                                  ├─ 重建浏览站与 index.md（tools/team_kb/build_site.py）
                                  ├─ 本地 git 提交，作者 = 上传人（只在 Worker 本地，便于回滚；不推送）
                                  ├─ 刷新内存搜索索引
                                  └─ 后台队列：外部 AI 生成功能卡片（§3.2）→ 写 cards/、重建、提交、刷新索引
组员 ──浏览器（内网 :8090）──► nginx：docsify 静态站 + 侧栏搜索框（调用 /api/search，服务端检索）
组员 ──飞书提问──► Gateway（规划器分类、存问题）◄──长轮询领取── team-kb 服务：检索 + 生成回答 ──► Gateway 回复飞书
```

- **数据只存 Worker**：Gateway（公网）不保存知识库内容，只转发问题和回答。
- **Gateway 不能主动访问 Worker**（Worker 主动拉取），所以飞书问答由 team-kb 服务向 Gateway 长轮询领取问题、检索、调用 AI 生成回答后交回（§5.1），不占用 Muliu Worker 的任务队列。

## 3. 数据模型（`/opt/team-kb`）

```text
/opt/team-kb/
  inbox/<上传批次>/          原始上传（保留，便于追溯）
  cases/<组别>/<作者>/<功能>.md   规范化用例（frontmatter + 统一表头；§3.1）
  cards/<功能>.md            功能卡片（§3.2）
  registry/features.csv     功能登记表（§3.3）
  index.md                  自动生成：按组别 / 功能 / 作者的总索引
  site/                     docsify 入口（index.html、_sidebar.md 自动生成）
```

### 3.1 规范化用例

沿用第 2 步已验证的规则：统一表头 `模块|二级模块|分级|测试项|前置条件|执行步骤|预期结果|实际结果|备注`；Excel 合并单元格向下填充模块 / 二级模块；空分级标「未分级」，不猜；其他表格与正文原样保留。frontmatter：功能名、组别、作者、来源、用例数、分级统计、模块列表、上传人、上传时间。

### 3.2 功能卡片

字段与第 2 步一致：一句话、简介、测试关注点、关键词、典型问题。上传后自动生成（Worker 调用 AI，规则同 `kb_card_prompt.md`，实现 `tools/team_kb/cards.py`）；已有卡片在用例未变时不重生成，用例更新则重生成。

- 发给 AI 的只有摘要：功能名、组别、作者、用例数、模块结构、最多 8 条样例（P0 优先），且所有命中敏感规则的值先打码（`normalize.mask_text`）；全文不出内网。Excel 单元格换行拆出的残片行（模块列是「2.停起服」之类）不进摘要。
- 模型配置在 Worker 的 `/opt/team-kb/ai.json`（chmod 600，不进任何 git）：与 Gateway 相同的中转，按顺序尝试，前一个失败或输出格式不符时换下一个。
- team-kb 服务后台单线程排队生成（一次 10–60 秒），上传结果提示「AI 在后台生成」；失败重试一次，仍失败只记日志，页面保持无卡片。生成期间用例又被更新则丢弃这次结果（新上传已重新排队）。
- 卡片提交到知识库本地 git，作者「AI 卡片」，说明里写模型名。
- 存量缺卡片的文件可手动补：`cards.py --missing [--limit N] [--write]`（不带 `--write` 只打印；写入后重启 team-kb 刷新索引）。

### 3.3 功能登记表（谁负责）

现有用例里只有「作者（测试）」，**没有策划、程序信息**，需要人工维护：

| 功能 | 别名 | 组别 | 测试 | 策划 | 程序 | 首次上线（赛季/版本） | 状态 | 相关功能 | 备注 |

- 初始版由脚本从用例生成（功能、组别、测试 = 作者），策划 / 程序留空；
- 组员通过上传 Excel / CSV 更新（网页上传，后续阶段），按「功能」合并，不整表覆盖。

## 4. 更新流程（组员，网页上传）

用户 2026-11-11 决定用网页上传（不用 Jenkins）。内网、无登录，靠「上传人必填 + 本地 git 记录作者 + 可回滚」追溯。

1. 浏览站侧栏「上传 / 更新资料」→ `upload.html`：上传人（必填，浏览器记住）、组别（系统组 / 赛季组 / 国服 / 其他）、测试（作者，默认同上传人）、`.md` 文件（一次 ≤ 20 个，每个 ≤ 3 MB）。
2. 浏览器读原始字节（base64）上传，服务端识别 UTF-8 / GBK。
3. 校验：文件名只能是 `.md`、不含路径字符，否则拒绝。命中 IP、密码、token、手机号、数据库地址规则的文件**不直接拒绝，交管理员审核**（§4.1）。
4. 规范化后写 `cases/<组别>/<测试>/<文件名>`：同路径 = 更新（内容相同显示「无变化」，不产生版本）；不同测试写同一功能 = 并存。Obsidian 属性块保留为一行「原文档属性」。
5. 结果表：新增 / 已更新 / 无变化 / 已拒绝，用例数、未分级数、提示（单元格换行串行、分级列混入文字、暂无或过期的摘要卡片）。
6. 原始上传保存在 `inbox/<时间>-<上传人>/`；浏览站与搜索在上传完成后立即更新。

### 4.1 命中规则的文件：管理员审核（2026-11-11 用户决定）

规则是固定正则，会误判（测试服 IP、文档里的示例密码等），目标机器也都在内网，所以不一刀切拒绝：

- Worker 把文件放进 `pending/<编号>/`（原文、规范化结果、元数据），上传人看到「待审核」。
- team-kb 服务每 15 秒把**未上报**的待审核项推给 Gateway（`POST /internal/team-kb/reviews`，Worker 令牌）：只含文件名、上传人、组别、目标路径、用例数、命中类型与行号、**命中值部分打码的命中行**（如 `10.***.40`、`密码：hu***22`），以及「内网查看全文」链接（`<内网站点>/api/pending/<编号>`，只有在内网能打开）。原文不离开 Worker。
- 运维页（ops，Cloudflare Access 仅管理员）新增「知识库审核」页签：待审核 / 已通过 / 已拒绝；可填备注，「通过并入库」或「拒绝」，记录审核人。
- team-kb 服务拉取决定（`GET /internal/team-kb/decisions`）：通过 → 写入 `cases/`、重建站点、本地 git 提交（作者 = 上传人，提交说明注明审核人）、刷新搜索；拒绝 → 移到 `pending/_rejected/`。结果回报 Gateway（`POST .../applied`），页面显示「已在内网处理」或失败原因。
- `pending/` 不进知识库 git，也不在静态站点目录下。

**功能卡片自动生成**：已接入（2026-11-11，见 §3.2）。未配置 `ai.json` 时自动关闭，上传结果提示「暂无摘要卡片」。

Excel 原件转换器（处理合并单元格、单元格内换行）是后续阶段的事；在此之前，单元格换行导致串行的文件在上传结果里提示「建议上传 Excel 原件或重新导出」。

## 5. 飞书问答（阶段 3，设计 2026-11-11）

### 5.1 链路

```text
组员 @机器人「亲卫队之前是谁测的」（群聊或私聊）
 → Gateway 规划器分类：kind = team_kb（§5.2）
 → Gateway 写入 team_kb_questions（同一个 SQLite）
 → Worker 上的 team-kb 服务长轮询 GET /internal/team-kb/questions（Gateway 最多挂起 25 秒，来了问题立即返回）
 → team-kb：检索内存索引（§5.3，不调用 AI）→ 组装打码后的上下文 → 外部 AI 写回答（§5.4）
 → POST /internal/team-kb/questions/{id}/answer
 → Gateway 在原消息下回复、写对话日志、任务完成
```

- **不经过 Muliu Worker 的任务队列**：由 team-kb 服务直接向 Gateway 领取问题，与测试服操作天然互不阻塞（满足「独立认领通道」），Muliu Worker 代码不改。
- Gateway 不保存知识库内容，只保存问题和最终回答（与现有对话日志一致）。
- **超时**：60 秒内没被领取（team-kb 停了 / 内网断了）或领取后 120 秒没回答 → 回复「组内知识库暂时不可用，请稍后重试，或到内网知识库站点搜索」，标记失败；之后迟到的回答丢弃。
- Gateway 重启：未完成的问题仍在 SQLite，重启后照常领取或超时。

### 5.2 分类（Gateway 规划器）

- 规划器新增 `kind:"team_kb"`：询问**游戏功能本身、测试用例、谁测过、某功能测试要注意什么、有没有类似功能**的问题；`steps` 为空，`summary` 写检索用的简短问题。
- 与现有 `kind:"knowledge"` 的边界：`knowledge` 只回答**机器人能做什么、脚本 / 测试服操作的用途、参数和风险**。
- 只有测试服操作限群内；知识库问答群聊、私聊都可以。
- 以「问题」开头、后跟空格 / 冒号 / 逗号的消息（「问题 浮桥谁测的」「问题：…」）不经规划器，直接走知识库（§5.7-1）；「问题是…」这类正常句子不受影响。

### 5.3 检索（team-kb 服务，确定性，不调用 AI）

- 问题切成中文二元组 + 英文 / 数字词，先去掉疑问词（是谁、什么、有没有、注意、之前…）。
- **功能级**：每个功能的标题（权重 4）、卡片关键词（2）、一句话 / 简介 / 测试关注点 / 模块名（1），按 IDF 加权打分，最多取 3 个功能（低于第 1 名 40% 的不取；最低分随功能数缩放，约等于命中一个少见词）。
- **用例行兜底**：功能级没命中时（细节只写在用例里，如「补兵额度用完后显示什么」），在全部用例行里按行级 IDF 检索：一行要覆盖问题 60% 的权重、且至少命中一半的词（不少于 2 个，忽略单字），再按命中行反推功能。
- **按人查**：问题里出现作者名（「金阳测过哪些功能」）→ 直接列出该作者的功能清单，不调用 AI。
- **用例级**：在候选功能的用例行里同样打分，取最多 12 行，P0 优先。
- 一个功能都没命中 → 不调用 AI，回复「组内知识库里没找到相关内容」，建议换个说法或到站点搜索。
- **实测**（2026-11-11，144 个功能、卡片里 432 条典型问题、不调用 AI，`qa.py --eval`）：第 1 名命中 96.3%，前 3 命中 99.3%；单次检索 ≤ 5 ms；「新的同盟建筑有没有类似的」「水战要注意什么」「补兵额度用完后界面显示什么」均命中合理功能。典型问题由卡片生成，结果偏乐观，上线前用组员真实问题再验（§7）。

### 5.4 回答

- 上下文：候选功能的卡片 + 组别 / 作者 / 用例数 + 命中的用例行（模块、分级、测试项 / 步骤、预期结果），整体打码（`normalize.mask_text`），≤ 6000 字。
- AI 规则：只依据上下文；先给结论；引用用例时注明「功能 · 作者」；没有依据就直说；不编造策划、程序、配置、数值；300 字以内。
- 模型：沿用卡片的 `ai.json`，按顺序尝试；实测 gpt-5.6-terra 一次回答 4–8 秒。AI 失败时不报错，改为列出最相关的功能和一句话简介。
- 来源只列回答里实际提到的功能（都没提到时列全部候选）。
- 回复（飞书文本，发出前再打码一次）：

```text
📒 组内知识库

<回答>

来源：浮桥 用例集（赛季组 · 金阳）、亲卫队（系统组 · 张宇杰）
```

- v1 单轮：不带上一轮上下文，「它有哪些 P0」这类指代可能答不准；后续需要时把上一轮命中的功能带进检索。

### 5.5 接口与存储（Gateway；Worker token + `X-Feishu-Worker-Id: team-kb`）

- `GET /internal/team-kb/questions?wait=25` → `{"items":[{"id","text","asked_at"}]}`，返回即标记 claimed。
- `POST /internal/team-kb/questions/{id}/answer` → `{"ok":true,"text","sources":[{"title","group","owner","path"}],"model","elapsed_ms"}`；`ok:false` 带 `reason`，Gateway 回复通用失败话术（不把内部原因发到飞书）。
- 表 `team_kb_questions`：id（= 飞书 message_id）、chat_id、text、status（pending / claimed / answered / failed）、asked_at、claimed_at、answered_at、answer、sources_json、model、error。
- 运维页：回答进入现有「问答」页签评审（§5.8），同时写对话日志。

### 5.6 实施顺序

1. team-kb：问答检索 + 回答生成 + 评测（`tools/team_kb/qa.py --eval / --ask`），本地与 Worker 上验证。（已完成）
2. Gateway：`team_kb_questions` 存储（`src/team_kb_questions.py`）、两个内部接口、超时处理、规划器 `team_kb` 分类与回复。（已完成）
3. team-kb：长轮询领取问题（`QuestionPoller`，3 个回答线程）、提交回答。（已完成）
4. 部署：先 Worker（team-kb，未接通时只记日志），再推送 Gateway；用户拉取重启 Gateway 后，在飞书试问一组问题。

### 5.7 已确认（2026-11-11）

1. 分类：规划器自动分类；另加前缀「问题」（用户 2026-11-11 改定，比「用例：」自然；后跟空格 / 冒号 / 逗号）强制走知识库，绕开误判。
2. 来源不附内网链接（IP 不进飞书消息），只写「功能（组别 · 作者）」。

### 5.8 问答评审与纠正（2026-11-11，用户要求：答错要能人工纠正、打补丁）

沿用现有问答评审（`docs/superpowers/specs/2026-11-04-qa-review-archive.md`，运维页「问答」页签），按 `domain` 区分：`script`（脚本资料问答）与 `team_kb`（组内知识库）。

- **记录**：知识库回答（ok）进入 `qa_records`（`domain=team_kb`，sources 含引用的功能与参考的归档编号），状态「待评审」；页面标「组内知识库」。
- **纠正**：「回答错误」→ 写正确说法 → Gateway 上的 AI 依据纠正说明和原回答重新回答（知识库资料在 Worker，重新回答不再检索；纠正说明是可信事实）。归档表单里答案可以直接手改。
- **归档**：类别固定「知识库」，「涉及功能」填引用的功能；不生成文档修正建议（用例资料在 Worker，修资料走重新上传）。
- **补丁生效**（立即）：
  1. 提问与某条知识库归档的标准问法完全相同 → Gateway 直接回复「📒 组内知识库（已审核答案，问答 #N）」，不调用 AI、不经过 Worker，记为「直接复用」；
  2. 相似（与脚本问答同一套匹配，最多 3 条）→ 随问题发给 team-kb（`references`），放在资料最前面，提示词要求相关时优先依据、与用例冲突时以它为准；检索没命中功能时也照样交给 AI 判断。
- **隔离**：脚本问答只用 `script` 归档，知识库问答只用 `team_kb` 归档；旧数据库启动时自动加 `domain` 列（默认 `script`）。

### 5.9 反馈、批量纠正与周末整包（2026-11-11 用户提出并确认）

流程：飞书 👍/👎 → 不满意的问答导出 Excel → 提问人填写正确回答 → 导入、确认、归档成补丁（立即生效）→ 周末 AI 把补丁合并进知识库「整包」。

1. **飞书反馈（已实现）**：知识库回答与脚本资料回答都改为卡片，带「👍 有用 / 👎 没答对」（`qa_feedback` 回调，不需要确认令牌）。看到的人都能点，以最后一次为准并记录点击人；回调只弹提示、不改卡片（3 秒内只写一条记录）。发卡片失败时退回纯文字。超时、失败提示仍是纯文字。
   运维页「问答」新增「不满意」筛选（👎 且尚未纠正归档：待评审 / 纠正中 / 直接复用）；每条显示 👍/👎；网页上可「标记不满意 / 取消不满意」。
2. **Excel 批量纠正（待做）**：「不满意」一键导出 xlsx（编号、时间、提问人、问题、机器人回答、引用来源、空列「正确回答」「填写人」）。导入时按编号匹配，填了正确回答的进入「待确认」；管理员浏览后一键全部归档或逐条修改（用户选择：先确认再生效）。依赖 openpyxl（Gateway 安装）。
3. **周末整包（待做）**：每周六凌晨由 Worker 的 team-kb 服务执行，只处理组内知识库补丁（脚本资料问答仍走「文档修正」）。
   - 拉取未合并的知识库归档，按「涉及功能」分组；

## 6. 浏览与搜索（内网）

- nginx 8090：根目录 `/opt/team-kb/site`（docsify 4.13.1，资源随站点存放，不依赖外网）；`/api/` 转发到 team-kb 服务。
- **搜索在服务端做**：docsify 自带搜索要在浏览器下载全部页面（4.5 MB）并在每次按键时扫描约 2.4 万行，明显卡顿（与 Python 版本无关：静态站点不经过 Python）。现由 team-kb 服务在内存里保存每条用例行与每个功能的摘要，按词全匹配优先、否则按中文二元组覆盖率（≥ 60%）排序，P0 略优先；单次查询约 20–40 ms，只返回前 10 个功能与前 40 条用例。
- 前端：侧栏搜索框停止输入 250 ms 后查询，结果高亮；点用例结果会跳到对应页面并定位、高亮那一行。

## 7. 检索效果评估

卡片里的「典型问题」（144 × 3 = 432 条）直接作为评测集：问题 → 期望命中的功能。每次改检索规则后在 Worker 上跑 `python3 /opt/team-kb/tools/qa.py --root /opt/team-kb --eval`，看第 1 名 / 前 3 命中率（2026-11-11：96.3% / 99.3%）。这些问题由卡片生成、偏乐观；上线后把组员在飞书里的真实提问（对话日志「组内知识库问答」）挑一批补进评测。

## 8. 何时升级到向量库

满足任一条件再考虑 Dify（Worker 已部署）或自建向量检索：数据量超过约 50 MB；评测集命中率在关键词检索下明显不够；或需要按语义找「类似功能」。Worker 上 Ollama 已有 `bge-m3` 嵌入模型，可直接复用。Markdown 仍是唯一数据源，向量库只是可重建的索引。
