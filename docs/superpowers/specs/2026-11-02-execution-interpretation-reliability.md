# 执行结果 AI 研读可靠性改造

> **状态：设计已定，待实施**  
> **日期：2026-11-02**  
> **关联计划：** [项目计划看板](../../hotfix-requirements-progress.html) STEP 24  
> **不变原则：** 可信执行终态先于 AI 展示；AI 永远不能将 `done` / `failed` / `submitted_result_unknown` 改写为另一种状态。  
> **适用范围（以 [执行结果确定性展示与典型故障库](2026-11-02-execution-report-library.md) 为准）：** 本文的后台研读机制**只处理模板库未命中的 `failed`**。`done` 与 `submitted_result_unknown` 走确定性模板、不调用 AI；下文涉及这两种状态的 AI 输入描述以上位文档为准。`execution_interpretations` 表结构以本文 §3.2 为准。

## 1. 触发事件与已确认事实

2026-11-02 的 2213 → 2018 合服结果回传中：

```text
11:41:59 execution result interpretation timed out
11:42:00 Worker /result 回传接受
```

Gateway 的 `execution_interpretation.enabled` 为 `true`，`timeout_seconds` 为默认 `8`。任务已先持久化为 `failed`，AI 研读超时后退回保底结果，因此飞书没有展示 AI 对日志的解释。

这不是 AI 没被调用，也不是 AI 可以越过安全边界把失败改成成功：

- Worker 可信结果先经 Gateway 校验并持久化 `done` / `failed` / `submitted_result_unknown`；
- 之后才调用 AI 研读；
- AI 超时、异常或空输出时回退可审计保底结果；
- AI 文本只能补充解释，不能覆盖终态。

## 2. 当前结构的问题

当前 Gateway `/internal/worker/jobs/{message_id}/result` 的链路：

```text
Worker 回传可信结果
→ Gateway 校验并持久化终态
→ 格式化保底结果
→ 同步等待 AI 研读（硬超时 8 秒）
→ 更新飞书卡片 / 返回 Worker accepted
```

### 2.1 8 秒总预算包住太多工作

当前 `asyncio.wait_for(..., timeout=8)` 包住完整 AI 研读：模型池选模型、模型自身 HTTP、模型内部重试、完整输出和解析。

但模型 HTTP 单次配置可达 60 秒，模型池失败后还可能尝试下一个模型；外层 8 秒先取消整个过程，慢但未报错的首个模型不会触发池内切换。

### 2.2 AI 阻塞结果投递

虽然状态已落库，但飞书卡片更新与 Worker `/result` 响应仍等待 AI 研读结束或超时。单纯把 8 秒提高会让：

- 用户更晚看到可信结果；
- Worker 更晚拿到 `accepted`；
- 慢模型、长日志、重试和池内切换继续互相争抢同一预算。

### 2.3 输入事实不完整

当前 AI 输入主要是清洗后的 `step_results[].log`。`failure_reason` / `result_unknown_reason` 是可信终态的重要原因，但未作为明确结构化字段拼进研读提示词。

有步骤日志时 AI 可能从日志中读到失败标记；没有日志的失败则无法根据可信原因解释。

### 2.4 可观测性不足

当前超时日志只含 `message_id`。无法区分：

- 哪个模型先被选中；
- 模型是否重试；
- 单模型耗时；
- prompt / 日志输入大小；
- 是排队慢、首 token 慢、网络超时还是池内切换耗尽预算。

## 3. 目标架构：可信结果先投递，AI 后台增强

```text
Worker 可信结果
→ Gateway 校验并持久化终态
→ 立即更新飞书为「可信保底结果」
→ 立即返回 Worker accepted
→ 创建持久化 AI 研读任务（pending）
     ↓ 后台领取
  结构化事实 + 受限日志 → 专用预算 / 模型策略
     ├─ 成功：只更新原卡片的「分析摘要」区域
     └─ 超时/失败：保留保底结果，不重复发消息，不改状态
```

### 3.1 结果卡的固定层级

卡片必须明确分层：

```text
可信终态：执行失败 / 执行完成 / 结果尚未核验   ← 机器状态，永远固定
执行明细：脚本、参数、可信失败原因、受控日志    ← 可审计事实
AI 分析：可选展示增强                              ← 可失败、可超时、不可改状态
```

即使 AI 认为日志「看起来完成」，也只能说：

```text
日志中出现完成类文本；但可信终态为失败，需按失败原因继续核验。
```

不能把卡片标题改成成功。

### 3.2 持久化后台任务，而非裸 `asyncio.create_task`

AI 研读是重要展示能力，不应因为 Gateway 重启而静默丢失。新增 SQLite 表（暂定名 `execution_interpretations`）：

| 字段 | 含义 |
| --- | --- |
| `message_id` | 与 `message_jobs` 一对一关联 |
| `status` | `pending` / `running` / `done` / `failed` / `timed_out` |
| `created_at` / `updated_at` | 生命周期 |
| `attempts` | 后台尝试次数 |
| `summary` | 脱敏后的 AI 摘要（成功才写） |
| `error_kind` | 超时 / 模型异常 / 卡片更新失败等受限分类 |
| `model_name` | 实际模型名，仅审计日志使用 |
| `input_chars` / `elapsed_ms` | 可观测性 |

Gateway 启动时恢复 `pending` / 过期 `running` 任务；不重放真实执行，只重放展示层研读。

## 4. 研读专用预算与模型策略

### 4.1 不复用通用聊天预算

| 项 | 当前 | 改后目标 |
| --- | --- | --- |
| 总等待 | 同步硬 8 秒 | 后台总预算，例如 30–45 秒（最终以实测 p95 定） |
| 单模型预算 | HTTP 可等 60 秒 | 有独立短截止，必须给下一模型留时间 |
| 输出 | 通用 `max_tokens`（可为 2048） | 研读专用较小上限，例如 300–500 token |
| 日志输入 | 最多 12,000 字符 | 结构化事实优先，关键日志分档截断 |
| 池策略 | 复用通用池，可能随机首选 | 研读专用、可预测的模型顺序；按 deadline 切换 |

具体秒数不在未量化前写死。上线前应先收集模型延迟数据。

### 4.2 截止时间感知的池调用

总预算应向每个模型调用传递绝对 deadline：

```text
总预算 40 秒
→ 模型 A 最多 12 秒（含至多一次短重试）
→ 失败/超时，模型 B 用剩余预算
→ 剩余时间不足时直接放弃，不继续重试
```

这与当前「随机挑首个模型，只有抛异常才换，外层 8 秒整体取消」不同。

## 5. 输入与提示词

AI 输入改为明确结构化事实：

```text
【可信终态】failed | done | submitted_result_unknown
【失败原因】failure_reason（若有）
【未知原因】result_unknown_reason（若有）
【步骤】编号、描述、脚本名、成功/失败、清洗后关键日志
【用户请求】脱敏后文本
【环境摘要】受限区域/服号信息
```

提示词规则：

1. 第一行必须先复述可信终态，不能自己改状态；
2. 日志中的“完成”“成功”等业务文本与机器失败终态冲突时，明确列出冲突，不裁决成功；
3. 只给排查建议、证据缺口与下一步核验，不建议自动重试写操作；
4. 不输出 URL、账号、密码、Cookie、Token、IP、数据库连接、工作目录、Task ID、私有路由标识。

## 6. 可观测性

每次研读至少记录以下受限指标（不记录原始敏感 prompt）：

```text
message_id
可信终态
候选模型顺序 / 实际模型
prompt_chars / 日志_chars / output_chars
每次模型耗时 / HTTP 状态或异常类别 / 重试次数
总耗时 / 是否回退 / 是否成功更新卡片
```

飞书卡片不显示这些内部指标；它们只写 Gateway 日志与 SQLite 审计。

## 7. 实施顺序

1. 新增研读任务 SQLite 状态表与恢复逻辑；
2. Worker 结果接口改为：落库 → 保底卡 → 创建研读任务 → 立即返回 accepted；
3. 实现后台研读 worker 与原卡片摘要更新；
4. 将失败原因 / 未知原因纳入结构化 AI 输入；
5. 实现专用总预算、单模型 deadline、受限输出；
6. 增加模型级耗时与回退可观测性；
7. 测试：成功研读更新卡、超时保留保底卡、重启恢复 pending、失败原因进 prompt、AI 不改终态；
8. 小范围部署后收集 p50/p95，再决定预算参数。

## 8. 不在本次范围

- 不让 AI 重试、重放或撤销任何真实运维操作；
- 不让 AI 将失败任务改成成功；
- 不用单纯提高现有 8 秒阈值掩盖问题；
- 不在飞书展示私有执行细节或模型池内部指标。

## 9. 验收标准

1. Worker `/result` 不再等待 AI 研读，可信保底卡立即可见；
2. AI 超时、异常、模型池耗尽时，用户仍只看到一次可信结果卡，不会静默；
3. AI 成功后更新原卡片，不创建重复消息；
4. 失败原因与可信终态进入 AI 输入，卡片标题仍由可信终态固定；
5. Gateway 重启后 pending 研读可恢复，真实执行绝不被重放；
6. 可从日志定位超时发生在哪个模型、哪次尝试、输入大小和总耗时。
