# 飞书内网知识库机器人建设方案

## 一、当前目标

当前阶段不是先做正式服务器部署，也不是马上做复杂 AI 入库，而是先解决核心问题：

> 知识库中有些内容没有进入索引，导致机器人搜不到，进而错误提示“本地知识库无相关内容”。

因此，当前优先级是：

```text
先补全文搜索能力
再优化搜索速度
再提升搜索准确率
最后再迁移正式服务器
```

---

## 二、当前系统现状

目前机器人已经具备基础能力：

1. 飞书消息接入；
2. 私聊或群聊 @ 机器人后触发回复；
3. 本地知识库检索；
4. 命中后基于本地知识库回答；
5. 回复中标注来源；
6. 未命中时在 `local_only` 模式下直接提示本地无相关内容；
7. 通过消息队列和 `message_id` 去重，避免重复回复；
8. 有阶段耗时日志，可以分析慢在哪里。

当前检索方式主要依赖三个索引文件：

```text
indexes/articles.json
indexes/concepts.json
indexes/qa.json
```

当前搜索逻辑是：

```text
先搜索引
索引命中 → 回答
索引未命中 → 认为知识库无相关内容
```

问题在于：

```text
如果 Markdown 文档存在，但没有进入索引，就会被漏搜。
```

这是当前最需要解决的问题。

---

## 三、建设路线总览

建议分四个阶段推进：

```text
阶段 1：全文搜索补漏
阶段 2：数据库全文索引
阶段 3：AI 入库增强
阶段 4：正式服务器部署
```

其中：

- 阶段 1 是现在马上要做的；
- 阶段 2 是文档量变大后做；
- 阶段 3 是提高搜索准确率；
- 阶段 4 是开发稳定后再迁移部署。

---

## 四、阶段 1：全文搜索补漏

### 目标

解决当前最直接的问题：

> 索引搜不到时，不要马上判断知识库无内容，而是继续扫描 Markdown 原文。

也就是把当前逻辑：

```text
索引搜索
  ↓
没命中
  ↓
直接提示无相关内容
```

改成：

```text
索引搜索
  ↓
没命中
  ↓
扫描 Markdown 原文
  ↓
Markdown 命中 → 基于原文回答
  ↓
Markdown 仍未命中 → 提示本地知识库无相关内容
```

### 新增配置

建议在 `knowledge_base` 中增加：

```json
"scan_markdown_when_index_miss": true,
"markdown_fallback_dirs": ["articles", "concepts", "qa"],
"markdown_fallback_max_files": 1000,
"markdown_fallback_max_file_chars": 20000
```

字段含义：

| 配置 | 说明 |
|---|---|
| `scan_markdown_when_index_miss` | 索引未命中时是否扫描 Markdown |
| `markdown_fallback_dirs` | 允许扫描的目录 |
| `markdown_fallback_max_files` | 最多扫描多少个文件，避免卡死 |
| `markdown_fallback_max_file_chars` | 单个文件最多读取多少字符 |

### 搜索流程

阶段 1 完成后的搜索流程：

```text
用户提问
  ↓
搜索 qa.json / concepts.json / articles.json
  ↓
如果索引命中
  ↓
读取命中文档
  ↓
交给 AI 回答，并标注来源
```

如果索引未命中：

```text
索引未命中
  ↓
扫描 articles / concepts / qa 目录下的 Markdown
  ↓
用当前规则打分
  ↓
分数达到 min_score
  ↓
读取 Markdown 原文
  ↓
交给 AI 回答，并标注来源
```

如果 Markdown 也未命中：

```text
本地知识库没有找到相关内容
```

### 阶段 1 完成标准

阶段 1 完成后，需要满足：

1. 已进入索引的内容仍然可以正常命中；
2. 未进入索引、但存在于 Markdown 文件中的内容也可以被搜到；
3. 回复中能显示来源文件路径；
4. 未命中时仍然遵守 `local_only`；
5. 日志中可以看到全文兜底扫描耗时；
6. 不明显拖慢索引命中的问题。

## 五、阶段 2：数据库全文索引

### 什么时候做

阶段 2 不建议现在马上做。

应该在出现以下情况后再做：

1. Markdown 文件数量明显增多；
2. 全文兜底扫描耗时变高；
3. 日志中 `knowledge_ms` 经常超过几百毫秒或 1 秒以上；
4. 项目组开始依赖机器人做日常查询。

### 目标

用数据库解决全文扫描变慢的问题。

推荐使用：

```text
SQLite FTS5
```

普通数据库适合存结构化数据，但全文搜索更适合用 FTS5。

### 数据库定位

数据库不应该取代原始知识库。

推荐关系是：

```text
Markdown / 飞书文档 / Git 文档 = 原始知识库
SQLite FTS5 = 可重建的搜索索引
```

也就是说：

```text
原文档是权威来源
数据库只是检索加速层
```

数据库坏了可以重建；原文档丢了才是真正的数据丢失。

### 数据库中存什么

可以设计两类表。

#### 1. 文档元数据表

```text
documents
- id
- path
- title
- kind
- content_hash
- mtime
- status
- updated_at
```

#### 2. 全文搜索表

```text
documents_fts
- title
- content
- path
- kind
```

搜索时先查 FTS5：

```text
用户问题
  ↓
FTS5 全文检索
  ↓
返回候选文档
  ↓
规则打分重新排序
  ↓
取前几条交给 AI
```

### 新文档如何入库

新增文档后，不需要手动写数据库。

应该通过同步器完成：

```text
新增或修改 Markdown
  ↓
运行 indexer sync
  ↓
计算文件 hash
  ↓
发现新增/修改/删除
  ↓
更新 SQLite FTS5
```

可以提供两个命令：

```bash
python -m src.indexer rebuild
```

用于全量重建。

```bash
python -m src.indexer sync
```

用于增量同步。

### 阶段 2 完成标准

1. 可以从 Markdown 全量构建 SQLite 搜索索引；
2. 新增文档后可以通过同步命令入库；
3. 删除文档后数据库不会继续返回旧内容；
4. 搜索速度比全量扫描稳定；
5. 数据库可以删除后重建；
6. 原 Markdown 知识库不受影响。

## 六、阶段 3：AI 入库增强

### 什么时候做

阶段 3 也不建议现在马上做。

它适合在基础全文搜索稳定之后再做。

原因是：

```text
先解决能不能搜到
再解决搜得快不快
最后再解决搜得准不准
```

AI 入库主要解决的是“搜得准”。

### AI 入库做什么

AI 不应该替代原文，也不应该决定是否删除文档。

AI 适合做辅助加工：

```text
自动摘要
自动提取关键词
自动提取概念
自动生成用户可能会问的问题
自动识别文档类型
自动标记是否需要人工复核
```

例如一篇文档是：

```text
飞书机器人事件订阅配置
```

AI 可以生成：

```json
{
  "summary": "说明飞书机器人如何配置事件订阅、Request URL、Verification Token 和消息接收事件。",
  "keywords": ["飞书机器人", "事件订阅", "Request URL", "Verification Token"],
  "questions": [
    "飞书机器人收不到消息怎么办？",
    "飞书事件订阅怎么配置？",
    "Request URL 怎么填写？"
  ],
  "doc_type": "guide",
  "review_required": false
}
```

这些内容可以一起进入数据库，参与搜索。

### AI 入库的价值

它可以解决这类问题：

```text
文档中写的是：事件订阅 Request URL
用户问的是：机器人为什么收不到消息？
```

纯关键词可能搜不到。

但如果 AI 入库时生成了问题：

```text
飞书机器人收不到消息怎么办？
```

以后用户这样问就更容易命中。

### 风险控制

AI 入库必须遵守几个原则：

```text
原文保留
AI 结果只作为辅助字段
不要让 AI 覆盖原文
不要让 AI 自动删除文档
回答时仍然引用原始来源
```

AI 可以提示：

```text
这篇文档可能过期
这篇文档像草稿
这篇文档缺少适用范围
```

但最终是否处理，应该交给人或规则决定。

### 阶段 3 完成标准

1. 新文档入库时能生成摘要、关键词、问题；
2. AI 生成内容能参与搜索；
3. 原文仍然保留；
4. 回答时仍然引用原文来源；
5. AI 元数据可重建；
6. AI 失败时不影响原文入库。

## 七、阶段 4：正式服务器部署

### 为什么放最后

当前阶段还在开发知识库能力。正式服务器迁移不应该放在前面。

原因是：

```text
功能还在变
配置还在调
检索方案还没稳定
```

所以部署到正式服务器应该放在：

```text
全文搜索稳定
数据库索引稳定
入库流程稳定
```

之后再做。

### 部署目标

最终目标是让项目组稳定使用：

```text
飞书群
  ↓
@知识库机器人
  ↓
稳定 HTTPS 服务
  ↓
内部知识库回答
```

### 推荐部署方式

可以部署到：

- 项目组内网服务器；
- 公司云主机；
- 部门 NAS；
- Kubernetes；
- 有稳定公网 HTTPS 的机器。

前面加：

```text
Nginx / Caddy / 公司网关
```

提供 HTTPS 回调地址：

```text
https://kb-bot.xxx.com/feishu/events
```

### 阶段 4 完成标准

1. 服务不依赖个人电脑；
2. 飞书回调 URL 稳定；
3. 服务有重启策略；
4. 日志可查看；
5. 配置文件和密钥安全管理；
6. 知识库路径稳定；
7. 有基础备份方案。

---

## 八、最终推荐路线

按优先级，建议这样推进：

```text
第一步：Markdown 全文兜底扫描
第二步：观察 knowledge_ms，判断是否需要数据库
第三步：SQLite FTS5 全文索引
第四步：文档入库同步器
第五步：AI 入库增强
第六步：正式服务器部署
```

更简洁地说：

```text
先补漏
再提速
再提准
最后上线
```

---

## 九、当前最应该做的事情

当前最应该立刻实现的是：

```text
索引未命中时，扫描 Markdown 文件兜底
```

这一步解决的是当前最真实的问题：

```text
知识库里有内容，但因为没有进入索引，所以机器人搜不到。
```

它不依赖数据库，也不影响后续升级。

实现后，如果发现：

```text
knowledge_ms 很低
```

说明全文扫描暂时够用。

如果发现：

```text
knowledge_ms 很高
```

再进入 SQLite FTS5 阶段。

---

## 十、一句话版本

当前路线应该调整为：

> 先把搜索补完整：索引搜不到时扫描 Markdown 原文；如果扫描变慢，再用 SQLite FTS5 做全文索引；等搜索稳定后，再用 AI 做入库增强；最后再迁移到正式服务器。
