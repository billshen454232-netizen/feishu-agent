# 测试服热更运行与验证总纲

> **维护状态：当前治理规则（持续更新）**
>
> **最后核对：2026-10-27**
>
> 当前架构、部署边界和唯一机器人侧调用合同见 [当前项目说明](architecture/current-project.md)。

## 1. 本文解决什么问题

本文规定热更需求如何从业务资料进入可维护、可审计的验证台账，并明确以下三类事实不能混为一谈：

1. **需求与字段证据**：用户提供的原始业务资料、明确确认和可复核的游戏内观察；
2. **本地实现与调用许可**：仓库中的注册表、代码、测试和 [Muliu 调用注册表](../config/muliu_script_catalog.md)；
3. **真实环境结果**：有权限维护者在已部署链路、目标服和游戏内取得的独立证据。

用户已确认“原始 Excel 的全部条目”是需求范围，不因单个条目的资料暂缺而缩小范围。这个范围约定不等于每一条都已经进入机器人执行许可，也不等于已经部署或游戏内生效。

## 2. 当前热更实现边界

当前可由仓库证明的主链为：

```text
config/muliu_script_catalog.md
← tools/sync_hotfix_planner_catalog.py
← tools/auto_hotfix_registry.py

/home/serverGeneralScript/auto_hotfix_tool.py
→ 导入 tools/auto_hotfix_registry.py
```

- 机器人只可生成 catalog 中精确登记的 `path + args` 合同；热更工具当前对应 `/home/serverGeneralScript/auto_hotfix_tool.py`。
- [tools/auto_hotfix_registry.py](../tools/auto_hotfix_registry.py) 是当前 catalog 同步使用的 Python 注册表；中文名和别名只用于受控意图路由，不能作为 Lua 表、字段、剧本或自由参数传递。
- [config/hotfix_thresholds.json](../config/hotfix_thresholds.json) 与 [tools/hotfix_threshold_registry.py](../tools/hotfix_threshold_registry.py) 是另一套未接入当前 catalog 同步主链的 JSON 资料模型。它们不应被称为当前唯一运行时来源或唯一执行白名单。
- [deployment/gs1/muliu_runner_manifest.json](../deployment/gs1/muliu_runner_manifest.json) 是 catalog 派生的候选部署资料；本仓库运行期不读取它，也不能证明 GS-1 存在或消费它。

新增或修改任一热更能力，必须同时更新精确调用合同、注册表、Planner 映射和相应测试；知识资料只说明用途、风险与验证边界，不能单独授予执行能力。

## 3. 证据优先级

对业务字段、Lua 目标、Patch 形态、剧本范围、端侧和游戏内效果，按以下顺序认定：

1. 用户提供的原始业务资料及其明确确认；
2. 目标测试服的可复核执行记录与游戏内观察；
3. 已提交且可定位的代码、配置、测试和 Git 历史；
4. 历史设计、截图、临时导出、旧硬编码或候选部署资料。

`docs/hotfix_thresholds_excel_export.json` 为 Git 忽略的本地导出资料，只能作为核对线索，不能替代原始资料或单独证明字段真值。

发现证据冲突或缺少决定性信息时：只将受影响条目标为“待确认”，记录唯一待确认问题；不得猜测字段、扩大许可、关闭其他已登记能力，或把不确定结论写成事实。

## 4. 单条条目的维护台账

每一个业务条目独立维护以下信息。可将台账置于受访问控制的项目记录中；不要把 URL、账号、密码、Token、IP、route identifier、原始服务器日志或其他敏感信息写入 Git。

```text
需求来源与定位信息
→ 中文标准名 / 受控别名
→ ASCII key
→ Lua 目标与数据形态
→ Patch 模板与范围
→ catalog 精确合同
→ 原请求人确认
→ 脚本层终态证据
→ 游戏内效果证据
```

其中任一环节未确认，不会阻塞其他证据充分的条目；该条不能被称为“已完成”。同一条目的字段证据、调用许可和环境结果应链接到各自独立的记录，避免一段描述同时承担三种事实。

## 5. 状态用词

| 状态 | 准确定义 |
| --- | --- |
| `已记录` | 已有需求来源或用户确认，尚未完成技术核对。 |
| `已核对` | 已按指定一手资料完成字段或范围核对；不表示可调用。 |
| `已登记调用合同` | 机器人侧 `path + args` 已精确登记并受测试覆盖；不表示 GS-1 已部署。 |
| `脚本层终态已取得` | 有可信回传表明本次 dispatcher / 脚本层已有终态；不表示游戏内生效。 |
| `游戏内已验证` | 已由可定位的人工观察或其他一手证据确认预期效果。 |
| `待确认` | 缺少决定性一手信息；禁止猜测或扩大调用。 |
| `已完成` | 该条的需求、受控模板、确认链路、所要求的执行证据和游戏内验证均已满足。 |

`submitted_result_unknown` 表示操作可能已提交但未取得可信结果。它不是失败，不应自动重放，也不能升级为任何“已验证”状态。

## 6. 受控推进顺序

1. **核对需求**：以原始业务资料和用户确认确定该条意图、字段和范围；不从中文相似词或旧代码猜测。
2. **实现本地能力**：将确认的 ASCII key、目标形态、Planner 映射和精确调用合同一起变更，并完成相应测试。
3. **候选部署核验**：由有权限维护者独立核验 GS-1 dispatcher、目标脚本、权限、日志协议和 Task 89 行为；仓库候选文件不构成部署证据。
4. **发起受控执行**：只在原请求人确认后，通过已登记合同执行；写操作仍遵守现有确认、租约和未知终态规则。
5. **区分验证层级**：记录脚本层回传；只有具备后置观察时再记录服务或游戏内效果。脚本退出成功、Patch 生成、上传、挂载或热更请求返回成功，都不能单独称为“游戏内已生效”。

本文件不授权真实 Muliu 调用、GS-1 覆盖、服务重启、配置修改或游戏内操作；这些动作由实际权限、调用合同与确认流程共同约束。

- 每次进展变化同步更新本文件、[当前项目说明](architecture/current-project.md) 和受影响的合同 / 测试 / 知识说明。

## 8. 最小本地检查

变更热更注册表、调用合同或派生产物后，在本地执行：

```bash
python -m pytest -v
python -m compileall src tests
python tools/generate_runner_manifest.py --check
python tools/sync_hotfix_planner_catalog.py --check
git diff --check
```

这些检查只说明本地代码与候选资料的一致性；不能替代实际部署、Muliu 调用、目标服状态或游戏内效果核验。
