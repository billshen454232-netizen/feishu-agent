# 测试服热更执行计划总纲

> **适用范围：** 飞书中文请求 → 受控 key → 人工确认 → 测试服 Patch。
> **目标不变：** Excel 中的全部配置条目都在交付范围内；条目形态不同应对应不同受控模板，不能因此从范围中移除。

## 0. 执行前强制自检

在读取、判断、改代码、更新计划或汇报前，逐项回答：

1. **这一步直接推进总目标吗？** 若不能，停止，不做无关扩展。
2. **结论来自哪份一手证据？** 不能指出具体来源时，不能把它写成事实。
3. **是否把“旧代码存在”“Patch 已生成 / 已挂载”误说成“字段正确”或“游戏内生效”？** 若是，改为准确状态。
4. **是否因单个条目不清楚而收缩、关闭或拒绝其他能力？** 若是，停止并改为只阻塞该条。
5. **证据互相冲突或不足吗？** 若是，暂停，向用户说明冲突和需要确认的唯一关键信息；不得猜测、绕过或另选依据。

## 1. 不可调换的实施顺序

1. **迁移现有逻辑：** 将当前脚本中已有的配置映射原样迁入独立注册表；只搬运，不新增、不删除、不纠错、不按 Excel 重解释。旧脚本是此阶段的行为基线，不是字段真值。
2. **人工回归验证：** 用户手动验证迁移后当前链路未受影响；未通过前不得加入 Excel 中的新条目或改变已有行为。
3. **扩展 Excel 条目：** 仅在迁移回归通过后，以原始 Excel 为唯一字段依据，逐项加入脚本中不存在的配置及专用 Patch 模板。
4. **游戏内效果验证：** 每项 Patch 链路通过后，再按用户指定的游戏内观察方式确认实际效果。

## 2. 证据优先级

字段、路径、数据形态、剧本范围、端侧和联动规则，按以下优先级认定：

1. 用户提供的原始 Excel：`C:\Users\v_shentao\Desktop\游戏服改配置.xlsx`；
2. 用户在对话中明确确认的事实；
3. 对应测试服的人工测试结果与可核验证据；
4. 已提交并可定位的代码、测试和 Git 历史；
5. 截图、旧硬编码、临时 JSON / 文档仅可作为待核对线索，**不能**覆盖前四类证据，也不能单独成为字段真值。

出现冲突时，以上位证据为准；仍无法判定时停止并询问用户。

## 3. 禁止推断

- 禁止从中文业务名、截图文字、相似字段名或旧映射猜测 Lua table、field、剧本、端侧、Patch 类型或联动写法。
- 禁止把“代码中存在映射”称为“已验证可用”。
- 禁止把“Patch 生成、上传、挂载或热更命令返回成功”称为“游戏内已生效”。
- 禁止把某一条资料缺失扩大为“关闭热更”“全部 reject”或缩小 Excel 全量交付范围。
- 禁止把计划、设计、静态检查或未运行测试称为“完成”。
- 禁止在与本总纲冲突时自行改写需求；必须先指出冲突并停止。

## 4. 单条记录的受控推进规则

每个 Excel 条目单独维护以下状态和证据：

```text
原始 Excel 行
→ 中文业务名 / 别名
→ ASCII key
→ Lua 目标与数据形态
→ Patch 模板
→ 调用合同
→ 人工确认卡
→ Patch 链路测试
→ 游戏内效果验证
```

任一环节缺失：只将该条标为“待确认”，记录缺少什么和唯一待确认问题；其他证据充分的条目继续推进。

## 5. 状态用词（不得夸大）

| 状态 | 含义 |
| --- | --- |
| `已记录` | 在原始 Excel 或用户确认中存在，但尚未完成技术核对。 |
| `已核对` | 已与原始 Excel 和指定证据对照；不表示可执行。 |
| `Patch 链路已确认` | 已确认生成、上传、挂载或触发链路；不表示游戏内效果已验证。 |
| `游戏内已验证` | 已由用户或可核验证据确认目标游戏效果。 |
| `待确认` | 该条缺少明确的一手信息；禁止猜测。 |
| `已完成` | 该条的目标模板、确认链路、测试证据和要求的游戏内验证均已满足。 |

## 6. 可视化计划更新规则

[热更需求推进页](hotfix-requirements-progress.html) 是当前进度的唯一简明视图。每次状态变化后：

- 只更新 `PLAN_DATA`；不得改动页面的 `<style>` 或渲染函数；
- 仅使用 `done`、`active`、`next`、`pending`；全页必须只有一个 `active`；
- `done` 只能对应有一手证据的已完成步骤；
- 当前步骤必须写清“现在要做什么”和“什么证据会使其完成”。
